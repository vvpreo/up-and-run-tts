# up-and-run-tts: сервис синтеза речи — потоковый и обычный

Статус: шаг 0 выполнен 30.09.2026, ждёт выбора модели пользователем. Сервис не начат.
Основание: [исследование от 30.09.2026](../research/README.md).

## Goal

Один самодостаточный Docker-сервис для русского TTS, который умеет и обычный
синтез (текст целиком → аудиофайл), и потоковый (текст от LLM приходит по
кускам → звук идёт сразу), с заменяемым движком за единым API.

## Context

Исследование рассматривало только озвучку потокового ответа LLM. Пользователь
расширил рамку: проект не должен ограничиваться потоковым синтезом, нужны обе
возможности.

Главное наблюдение, на котором стоит план: **для русского оба режима — это один
и тот же конвейер.** Любой русский движок работает через нарезку на
клаузы/предложения, поэтому «обычный» синтез — это конвейер, которому текст дали
сразу целиком, а «потоковый» — тот же конвейер, которому текст дают по мере
появления. Разница только в транспорте и в том, когда нарезчик получает данные.
Значит, второй режим почти бесплатен, если первый построен правильно.

Факты о железе (проверено на боксе 30.09.2026):

- CPU: Intel i7-8750H, 6 ядер / 12 потоков, AVX2 есть — Silero запустится.
  Это ноутбучный процессор, заметно слабее i9-10940X, на котором авторы Silero
  получили 36× реального времени. Реальная скорость неизвестна до замера.
- RAM: 62 ГБ, свободно ~35 ГБ.
- GPU: GTX 1050 Ti, занято 3,1 из 4 ГБ (распознавание) — для TTS не используется.
- DGX Spark — только по явному указанию пользователя.

## Архитектура

```
            ┌────────────────────── транспорты ───────────────────────┐
            │ HTTP  POST /v1/audio/speech        (текст целиком → файл │
            │                                     или chunked-аудио)   │
            │ WS    /v1/audio/speech/stream      (текст кусками → PCM) │
            │ (позже) Wyoming, ElevenLabs-совместимый WS, async jobs   │
            └───────────────────────────┬─────────────────────────────┘
                                        ▼
   фильтр разметки → нарезчик → нормализация → «ё» и ударения   ← общий конвейер
   (markdown, код,   (клаузы /   (числа, даты,   (только для движков,
    ссылки, эмодзи)   предлож.)   сокращения,     которым это нужно)
                                  латиница)
                                        ▼
                         интерфейс движка: фрагмент → PCM
            ┌───────────────┬───────────────────────┬──────────────────┐
            │ Silero (CPU,  │ удалённый OpenAI-     │ (опц.) Piper —   │
            │ в процессе)   │ совместимый движок    │ aarch64 / без    │
            │ — по умолч.   │ (Qwen3-TTS на Spark)  │ PyTorch          │
            └───────────────┴───────────────────────┴──────────────────┘
                                        ▼
        упорядоченная очередь аудио с id генерации (отмена при перебивании)
                                        ▼
              кодирование: pcm / wav / mp3 / opus / flac; 8 / 24 / 48 кГц
```

## Что входит в «и те, и другие возможности»

**Обычный синтез (текст известен целиком)**

- `POST /v1/audio/speech` в формате OpenAI: `model`, `input`, `voice`,
  `response_format`, `speed`. Подключается к Open WebUI, LiveKit, Pipecat,
  `wyoming-openai` без доработок.
- Длинный текст (статья, глава): внутренняя нарезка, паузы между абзацами,
  склейка в один файл. Ограничения на длину нет.
- Тот же запрос с потоковой выдачей: аудио уходит по мере готовности
  предложений, первый звук — после первого предложения, а не после всего текста.
- Подмножество SSML там, где движок его понимает (у Silero — темп, высота, паузы).
- `GET /v1/voices` — список голосов с движком и лицензией каждого.
- Дешёвые дополнения, которые даёт попредложенческий синтез: тайминги
  предложений (субтитры SRT/VTT), кэш повторяющихся фраз, сценарий из
  нескольких голосов в одном файле.
- Для очень длинных текстов (книга) — асинхронные задания: поставить, опросить
  статус, скачать. Отдельный шаг, по необходимости.

**Потоковый синтез (текст ещё пишется)**

- WebSocket `/v1/audio/speech/stream` с набором сообщений vLLM-Omni:
  клиент шлёт `session.config`, `input.text`, `input.done`; сервер —
  `audio.start`, бинарные PCM-кадры, `audio.done`. Это единственный открытый
  образец такого протокола, и за ним же позже встанет Qwen3-TTS.
- Инкрементальный нарезчик с коротким первым фрагментом и списком русских
  сокращений («т.е.», «г.», даты с точками).
- Отмена по id генерации (перебивание), сервер сообщает, сколько реально отдано.
- Демо-страница: текстовое поле, имитация потока LLM, проигрыватель на
  AudioWorklet. Она же — стенд для приёмки на слух.

## Варианты устройства проекта

| Вариант | Суть | Плюсы | Минусы |
|---|---|---|---|
| **А. Один сервис со встроенным Silero** | Как `up-and-run-stt`: один образ, CPU, оба режима API | Быстрее всего до результата; один контейнер | Клонирования и «дизайна» голоса нет; смена движка — переписывание |
| **Б. Шлюз с подключаемыми движками** | Конвейер и протоколы отдельно от движка; Silero в процессе, GPU-модели — удалённо по HTTP | Движок выбирается полем `model`/`voice`; Spark подключается без тяжёлых зависимостей в образе | Чуть больше кода в начале (интерфейс движка) |
| **В. Набор отдельных образов по движкам** | `:silero`, `:qwen3`, `:piper`, у каждого свой сервер | Буквально «PnP implementations» из README | Конвейер дублируется или выносится в библиотеку; сопровождение ×N |

**Рекомендация: А, написанный как Б.** Интерфейс движка закладывается с первого
дня (это один небольшой класс), но реализуется сначала только Silero. Удалённый
движок добавляется на шаге 5 без переделки API. Вариант В не нужен: разные
поставки получаются тегами одного образа.

## Steps

Порядок изменён 30.09.2026 по решению пользователя: сначала лучший возможный результат
на Spark и замер ресурсов, оптимизация и перенос на Development Box — потом. Лицензия
на этом этапе не учитывается.

0. **Сравнение качества на Spark — сделано 30.09.2026.** Восемь GPU-моделей и Silero,
   два сценария (фраза целиком и текст по кускам), страница с образцами.
   Итог: [отчёт](../research/spark-quality-benchmark.md). Отклонения от первоначального
   замысла: добавлены Fish S2 Pro, VoxCPM2, OmniVoice и Chatterbox V3; замер Silero на
   процессоре бокса сделан здесь же (17× реального времени).
1. **Выбор модели на слух.** Пользователь слушает страницу `http://devbox-ubu.ssh:9018`
   и оценивает. По измеримым признакам вперёд выходят F5-TTS RU v4 и Qwen3-TTS 1.7B.
   Зависит от: 0.
2. **Оптимизация победителя на Spark.** Ускоренные пути (CUDA-графы у Qwen3-TTS, меньше
   шагов диффузии у F5-TTS), прогрев, замер задержки до первого звука и памяти под
   нагрузкой. Зависит от: 1.
3. **Каркас сервиса и обычный синтез.** FastAPI, интерфейс движка, выбранный движок,
   `POST /v1/audio/speech` в формате OpenAI (wav, pcm, mp3, opus, flac) с потоковой
   отдачей, `GET /v1/voices`, `/health`, Bearer-авторизация. Docker:
   `name: up-and-run-tts`, контейнер `up-and-run-tts-api`, том для весов. Первый
   потребитель известен — голосовой агент `archfam-v3` (короткие реплики, pcm16 24 кГц,
   воспроизведение до конца синтеза). Зависит от: 1.
4. **Конвейер текста.** Фильтр разметки, нарезчик по клаузам (минимальная длина фрагмента;
   пунктуация между цифрами — не граница), нормализация чисел, дат, сокращений и латиницы,
   расстановка ударений со словарём исправлений. Прогон показал, что цифры надёжно не
   читает ни одна модель, а оба расстановщика ударений ошибаются. Зависит от: 3.
5. **Потоковый ввод текста.** WebSocket, очередь с id генерации, отмена, демо-страница.
   Модели с нативным потоковым вводом (MOSS, CosyVoice 3) себя не оправдали, поэтому
   основа — нарезка по клаузам. Протокол — ElevenLabs `stream-input` или vLLM-Omni,
   решение после шага 1. Зависит от: 4.
6. **Перенос на Development Box.** GPU бокса не подходит (свободен ~1 ГБ из 4). Путь —
   процессор: Silero как запасной движок, проверка CPU-сборки OmniVoice. Зависит от: 3.
7. **Упаковка и публикация.** README в стиле `up-and-run-stt`, образ. Здесь же
   вернуться к лицензиям: F5-TTS RU (Misha24-10) и Fish S2 Pro некоммерческие.

## Open questions

1. **Какая модель звучит лучше** — решается прослушиванием (шаг 1).
2. **Где живёт сервис.** На Spark (общий ресурс, GPU-модели) или на боксе (только
   процессор и Silero) — зависит от выбора модели.
3. **Голос.** Клон конкретной записи, голос по описанию или готовый — и чей голос брать
   за образец для клонирования.
4. **Протокол для потокового текста** — ElevenLabs `stream-input` (есть готовые клиенты)
   или набор сообщений vLLM-Omni.
5. **Языки.** Принято по умолчанию: только русский; английские слова — через
   нормализацию в кириллицу.
